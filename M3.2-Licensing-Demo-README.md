# Staff Payroll — Licensing + Configurable Demo Policy Implementation v0.9.0

## Final demo decision
A customer can start a configurable demo directly from the app. A separate customer-facing license key is not required.

### Self-service demo
1. Tap `Start Free Demo`.
2. Enter email, name, business/company name, password and confirmation.
3. Firebase creates the authentication account.
4. The app sends a Firebase email verification message.
5. Customer verifies the email and returns to the app.
6. Tap `I Have Verified My Email`.
7. The app creates the demo tenant, demo license, first user and audit history in one transaction.
8. The customer becomes the tenant Super Admin.

Default self-service demo entitlement:
- Validity: the configured demo duration
- Staff limit: 5
- Device limit: 2
- Current implementation modules enabled

The email must be verified before the demo can be activated. An email that already has a license cannot self-start another demo.

## Sales-team demo
Developer / License Team can also issue a configurable demo to a specific customer email from `Create / Issue License` by selecting `Demo`.

Flow:
1. License Team selects `Demo`.
2. Enter customer/business name and email.
3. Default demo limits are 5 staff / 2 devices and validity is the configured demo duration.
4. Customer creates the account using the same email.
5. Customer verifies the email.
6. Customer signs in and completes onboarding.

## OTP decision
Numeric SMS OTP is intentionally not used in this Spark-only implementation. Firebase currently requires a linked Cloud Billing account for Phone Auth SMS, so SMS OTP would conflict with the project's Spark-only constraint. Firebase supports email verification/email-link authentication, which verifies control of the email address without requiring SMS billing.

If a future requirement specifically demands a numeric email OTP (for example, a 6-digit code), that should be added as a separate trusted email-OTP service using an external mail provider or backend. It should not be implemented by exposing an email-provider secret in the Android app.

## Security
- Self-service demo writes are restricted by Firestore rules to the authenticated, email-verified account and deterministic demo document IDs.
- Demo license limits are enforced by rules for the self-service path.
- Existing paid-license issuance remains Developer/License-Team controlled.
- Customer business-data collections remain closed in this milestone.


## Demo Device Anti-Reuse + Lead Tracking (v0.9.0)
- A stable Android device identifier is used for demo history tracking.
- Once a device has consumed a demo, self-service activation is blocked with: “Demo already used on this device/account. Kindly buy the license.”
- A blocked customer can submit name, business, email and mobile number for a Sales callback.
- Developer / Sales Team can view demo leads from `Demo Leads`.
- Developer / Sales Team can use `Reset / Allow Re-Demo` to grant exactly one additional demo on a previously used device.
- Reset does not erase history; every activation/re-activation remains in `licenseHistory`.
- New demos use the current configurable Demo Policy. Existing demos retain their issued terms.
- The anti-reuse ledger is stored in `/demoDeviceHistory`; lead records are stored in `/demoLeads`.


## Demo Reuse Protection + Sales Reset + Lead Tracking (v0.9.0)
- Stable Android device ID is used for demo anti-reuse tracking.
- A device that has already consumed a demo is blocked from self-service reactivation, even after uninstall/reinstall.
- Blocked customers can submit name, business, mobile and email for a Sales callback.
- Developer can view Demo Leads and Demo Activations.
- Developer can grant exactly one additional demo using Reset / Allow Re-Demo. Reset never deletes historical records.
- Existing demo accounts can sign in through the demo screen after a Sales reset and activate the new demo.
- Every activation is appended to `licenseHistory` and `demoActivations` for lead tracking.
